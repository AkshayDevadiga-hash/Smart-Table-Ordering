# Smart Restaurant Ordering System
## Complete Project Documentation

---

## Executive Summary

A full-stack **QR code-based restaurant management system** that enables:
- Customers to order directly via QR code (no waiter needed)
- Kitchen staff to view live orders on a dashboard
- Admin to manage menu, tables, and view reports
- Customers to call a waiter directly from their table
- Customers to pay online (simulated gateway) or request cash collection via waiter

**Tech Stack**: Express.js + TypeScript + PostgreSQL + Vanilla HTML/CSS/JavaScript

---

## Project Overview

### What Problem Does It Solve?

Traditional restaurant ordering has multiple pain points:
- Waiters take time to take orders
- Manual errors in order placement
- Kitchen can't see orders in real-time
- No quick payment processing
- Difficult inventory management
- Customers have no way to signal for assistance without shouting or waving

**Our Solution**: Self-service ordering with live kitchen tracking, a built-in waiter call system, and dual payment modes (online simulation + cash collection)

## New Feature: Dual Payment Mode

When an order's status reaches **"Delivered"**, the customer is shown a payment screen on their order tracking page (`/order/:orderId`). They choose between two methods:

---

### Option A — Online Payment (Simulated)

Since there is no real payment gateway integrated, the system shows a **simulated payment UI** that mimics a UPI / card flow:

**Steps shown to customer**:

1. Payment screen appears with order total and two tabs: "UPI" and "Card"
2. **UPI tab**: Customer enters a fake UPI ID (e.g. `name@upi`) and presses Pay
3. **Card tab**: Customer enters fake card number, expiry, and CVV and presses Pay
4. A 2-second loading spinner plays ("Processing payment...")
5. Success screen shown — "Payment Successful! Thank you."
6. `PATCH /api/orders/:id` is called with `{ paymentStatus: "paid", paymentMethod: "online" }`
7. Order page updates to show paid badge

**What is simulated**: All card/UPI details are accepted as-is with no real validation or gateway call. This is intentional — it demonstrates the payment UX without real money movement.

**Fake UPI fields**:

| Field | Placeholder | Validation |
|-------|-------------|------------|
| UPI ID | `yourname@upi` | Must contain `@`, min 5 chars |
| Amount | Pre-filled, read-only | From order total |

**Fake Card fields**:

| Field | Placeholder | Validation |
|-------|-------------|------------|
| Card Number | `1234 5678 9012 3456` | 16 digits, spaces auto-inserted |
| Expiry | `MM/YY` | Format check only |
| CVV | `123` | 3 digits |
| Name | `Card Holder Name` | Non-empty |

---

### Option B — Cash Payment

Customer selects **"Pay by Cash"**. The system:

1. Calls `POST /api/waiter-requests` with `type: "cash_collection"` and the `orderId`
2. Sets `paymentMethod: "cash"` on the order
3. Shows the customer a waiting screen: "A waiter will come to collect payment shortly."
4. The customer page polls every 10 seconds; once admin confirms, it shows "Payment Confirmed!"

---

### Admin Side — Cash Payment Requests

A dedicated **"Cash Payments"** panel appears on the Admin Dashboard, separate from the general waiter request list.

**Panel behaviour**:
- Polls `GET /api/waiter-requests?type=cash_collection&status=pending` every 10 seconds
- Shows table number, order total, and time elapsed
- Admin presses **"Confirm Payment Received"** after waiter physically collects cash
- On confirm, the backend updates both the waiter request (`status: "resolved"`) and the order (`paymentStatus: "paid"`)

**Cash Payment Panel Columns**:

| Column | Description |
|--------|-------------|
| Table | Table number |
| Order ID | Short order reference |
| Amount Due | Order total (with tax) |
| Requested At | Time customer pressed "Pay by Cash" |
| Action | "Confirm Payment Received" button |

**Visual Indicators**:
- Cash payment requests shown with an amber badge in the admin sidebar
- Once confirmed, entry moves to a "Completed" sub-list and auto-hides after 30 seconds
- The admin order list also updates the payment status badge from "Pending" to "Paid"

---

### Payment Flow Summary

| Step | Online | Cash |
|------|--------|------|
| Customer action | Fills fake UPI/card form | Presses "Pay by Cash" |
| System action | Marks order paid instantly | Creates waiter request (cash_collection) |
| Waiter involvement | None | Waiter visits table to collect |
| Admin action | None needed | Clicks "Confirm Payment Received" |
| Order marked paid | Immediately | After admin confirmation |

## New Feature: Call Waiter

### Customer Side — Tables Page

A **"Call Waiter"** button is displayed prominently on the customer-facing table page (`/menu/:tableId`). When tapped:

1. A `POST /api/waiter-requests` call is made with the current `tableId`.
2. The button temporarily changes to "Request Sent" and is disabled for 60 seconds to prevent duplicate requests.
3. If the waiter has not acknowledged within 3 minutes, the button re-enables automatically.

**UI Placement**: Below the cart summary, above the "Place Order" button.

**Button States**:

| State | Label | Icon | Behaviour |
|-------|-------|------|-----------|
| Default | Call Waiter | Bell icon | Sends request |
| Sent | Request Sent | Check icon | Disabled for 60s |
| Acknowledged | Waiter Coming | Person icon | Informational |

---

### Admin Side — Waiter Request List

A new **"Waiter Requests"** section is added to the Admin Dashboard (`/admin`). It appears as a live panel in the sidebar or as a dedicated tab.

**Panel behaviour**:
- Polls `GET /api/waiter-requests?status=pending` every 10 seconds
- Shows table number, time elapsed since request, and optional note
- Admin can mark a request as **Acknowledged** or **Resolved** inline

**Request List Columns**:

| Column | Description |
|--------|-------------|
| Table | Table number |
| Requested At | Time of request (e.g. "2 min ago") |
| Note | Optional customer note |
| Status | Pending / Acknowledged / Resolved |
| Action | Acknowledge or Resolve button |

**Visual Indicators**:
- Pending requests shown with a red badge count on the admin sidebar
- Acknowledged requests shown in amber
- Resolved requests auto-removed from the live list after 30 seconds

## New API Routes

### Waiter Requests

| Method | Route | Purpose | Auth |
|--------|-------|---------|------|
| POST | `/api/waiter-requests` | Customer calls waiter or requests cash collection | No |
| GET | `/api/waiter-requests` | List requests (filterable by type & status) | Yes |
| PATCH | `/api/waiter-requests/:id` | Acknowledge or resolve | Yes |

#### POST `/api/waiter-requests`
**Request body**:
```json
{
  "tableId": 3,
  "type": "assistance",
  "note": "Need extra napkins"
}
```
For cash payment:
```json
{
  "tableId": 3,
  "orderId": 42,
  "type": "cash_collection"
}
```
**Response**:
```json
{
  "id": 17,
  "tableId": 3,
  "type": "cash_collection",
  "status": "pending",
  "requestedAt": "2025-05-25T10:32:00Z"
}
```

#### GET `/api/waiter-requests`
**Query params**: `type=assistance|cash_collection`, `status=pending|acknowledged|resolved`

**Response**:
```json
[
  {
    "id": 17,
    "tableId": 3,
    "tableNumber": "T-03",
    "orderId": 42,
    "orderTotal": "342.00",
    "type": "cash_collection",
    "status": "pending",
    "note": null,
    "requestedAt": "2025-05-25T10:32:00Z"
  }
]
```

#### PATCH `/api/waiter-requests/:id`
**Request body**:
```json
{ "status": "resolved" }
```
When resolving a `cash_collection` request, the backend also automatically sets `paymentStatus: "paid"` and `paymentMethod: "cash"` on the linked order.

### Payment (Order Update)

| Method | Route | Purpose | Auth |
|--------|-------|---------|------|
| PATCH | `/api/orders/:id/pay` | Mark order as paid (online simulation) | No |

**Request body**:

**Response**:
```json

  "id": 42,
```

## Three Critical Technical Aspects

### 1. Database Sync (Drizzle ORM)

**Problem**: Manual SQL migrations are error-prone and hard to maintain.

**Solution**: TypeScript-first schema definition with automatic database sync.

#### How It Works:

```typescript
// Define table in TypeScript (backend/src/db/schema.ts)
export const menuItemsTable = pgTable("menu_items", {
  id: serial("id").primaryKey(),
  categoryId: integer("category_id").notNull()
    .references(() => menuCategoriesTable.id, { onDelete: "cascade" }),
  name: text("name").notNull(),
  price: decimal("price", { precision: 10, scale: 2 }).notNull(),
  isVeg: boolean("is_veg").notNull().default(false),
  icon: text("icon").default("utensils"),  // Lucide icon name
  createdAt: timestamp("created_at").defaultNow().notNull(),
});

export const waiterRequestsTable = pgTable("waiter_requests", {
  id: serial("id").primaryKey(),
  tableId: integer("table_id").notNull()
    .references(() => restaurantTablesTable.id, { onDelete: "cascade" }),
  orderId: integer("order_id")
    .references(() => ordersTable.id, { onDelete: "set null" }),  // for cash_collection
  type: text("type", { enum: ["assistance", "cash_collection"] })
    .notNull().default("assistance"),
  status: text("status", { enum: ["pending", "acknowledged", "resolved"] })
    .notNull().default("pending"),
  note: text("note"),
  requestedAt: timestamp("requested_at").defaultNow().notNull(),
  acknowledgedAt: timestamp("acknowledged_at"),
  resolvedAt: timestamp("resolved_at"),
});

// Deploy with single command
$ pnpm run db:push
```

#### Benefits:
- No SQL writing — define schema in TypeScript
- Type safety — all queries are auto-typed
- Version control — schema changes tracked in git
- Instant deployment — one command deploys changes
- IDE autocomplete — full IntelliSense support

---

### 2. Validation (Zod)

**Problem**: Bad API requests can corrupt the database (SQL injection, type mismatches, invalid data).

**Solution**: Every API request validated with Zod schemas before processing.

#### New Validation Schemas (Waiter Requests & Payment):

```typescript
export const CreateWaiterRequestBody = zod.object({
  tableId: zod.number().int().positive(),
  orderId: zod.number().int().positive().nullish(),  // required for cash_collection
  type: zod.enum(["assistance", "cash_collection"]).default("assistance"),
  note: zod.string().max(200).nullish(),
});

export const UpdateWaiterRequestBody = zod.object({
  status: zod.enum(["acknowledged", "resolved"]),
});

export const PayOrderBody = zod.object({
  paymentMethod: zod.enum(["online", "cash"]),
});
```

#### What Gets Caught:

| Input | Validation | Result |
|-------|-----------|--------|
| `tableId: "abc"` | Not a number | Rejected |
| `tableId: 3` | Valid integer | Accepted |
| `status: "invalid"` | Not in enum | Rejected |
| `status: "acknowledged"` | Valid enum | Accepted |
| `note: undefined` | Optional field | Accepted |

---

### 3. Easy Deployment

**Problem**: Complex multi-file deployments are slow and error-prone.

**Solution**: Single bundled file with automated Railway deployment.

#### Build Process:

```
TypeScript Source Code (src/)
        |  [esbuild compiles & bundles]
        |
Single JavaScript File (dist/index.mjs)
```


## Development Setup

### Prerequisites
- Node.js 24+
- pnpm (package manager)
- PostgreSQL database

### Local Installation

```bash
# 1. Install dependencies
pnpm install

# 2. Configure environment
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env

# 3. Fill in .env files
# backend/.env:
#   DATABASE_URL=postgresql://...
#   JWT_SECRET=your-secret
#   ADMIN_PASSWORD=admin1234
# frontend/.env:
#   API_URL=http://localhost:5000

# 4. Create database schema (includes new waiter_requests table)
pnpm --filter @workspace/backend run db:push

# 5. Start development
pnpm run dev
```

### Development Ports
- **Backend**: 5000 (set `PORT` in backend/.env)
- **Frontend**: 3000 (set `PORT` in frontend/.env)

### Useful Commands

```bash
pnpm run typecheck
pnpm run build
pnpm --filter @workspace/backend run build
pnpm --filter @workspace/backend run db:push
pnpm --filter @workspace/backend run db:push-force
pnpm run dev
```

## Deployment to Production

### Option 1: Railway (Recommended)

1. Connect Repository — go to railway.app, connect GitHub repo
2. Add Environment — `DATABASE_URL`, `JWT_SECRET`, `ADMIN_PASSWORD`, `CLIENT_URL`
3. Deploy — push code to GitHub; Railway auto-builds and deploys

### Option 2: Docker

```dockerfile
FROM node:24-alpine
WORKDIR /app
COPY . .
RUN pnpm install
RUN pnpm run build
CMD ["node", "backend/dist/index.mjs"]
```
